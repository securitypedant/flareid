# Languages and accessibility

The pages people sign in through are translated and built to WCAG 2.2 AA:

- the sign-in page (password and passkey),
- the second step (authenticator app or backup code, email code, security
  questions, passkey),
- the consent page,
- the sign-out confirmation and the front-channel "Signing you out" page,
- password recovery, reset and invitation pages,
- the sign-in error and message pages (expired sign-in, app misconfigured,
  signed out, ...),
- the first-run `/setup` page.

The admin console and My account (including the forced second-factor
enrolment page, which is a My account page) are English. Their pages carry
`<html lang="en">`.

FlareID ships **English** (the source), **French** and **German**. The French
and German files are machine-assisted and marked so in their metadata
(`_meta.machineAssisted`): native-speaker review is very welcome.

## Which language a page is shown in

First match wins (`requestLocale` in `src/lib/login-views.ts`):

1. **`?lang=<code>`** on the request - `/login?lang=fr`, or any other of the
   pages above. It is remembered in a `flareid_lang` cookie (a year,
   `Secure; HttpOnly; SameSite=Lax`; it holds only the language code).
2. **The `flareid_lang` cookie** - the language the person picked before.
3. **The sign-in flow's language** - the one the sign-in page was shown in,
   carried inside the sealed sign-in flow (and the pending second step), so the
   pages that answer its form posts stay in that language even when the
   browser blocks the cookie. For an OIDC sign-in this starts as the first
   language FlareID has in the app's **`ui_locales`** parameter (OIDC Core
   3.1.2.1), which also applies to the consent page after it.
4. **`Accept-Language`**, by q-value. A regional tag falls back to its
   language: `fr-CA` gets French, `de-AT` German.
5. **The instance default**: Admin → Branding → Language → *Default language*
   (or `PATCH /api/v1/branding` with `default_language`). English unless
   changed. It is the same for every brand.

An unknown `?lang=` value is ignored.

The sign-in page has a language picker in its footer. Each link goes to
`/login/language?lang=<code>&flow_id=<flow>`, which shows the same sign-in -
the same app, the same brand - in that language (and sets the cookie), so
switching never loses an OIDC or SAML request in progress.

## What is not translated

- Text an administrator writes: a brand's custom sign-in message (the built-in
  default, "Sign in to continue.", *is* translated), app and client names,
  security question wording.
- Technical reasons meant for an app's administrator, which stay in English
  inside a translated page: under "This app can't sign you in", the reason
  (*The address it asked to return to (redirect_uri) is not registered for
  it.*) is followed by the translated "The app's administrator needs to check
  its sign-in configuration." The same goes for sign-out request errors
  (RP-initiated logout and SAML Single Logout).
- Errors from the account rules at `/setup` (username format, domain format),
  which come from the same service code as the API.
- Emails (invitation, reset, sign-in code): their wording is configurable per
  instance under Branding → Email templates.
- The SAML "Signing you in..." auto-submit page, which a browser shows for a
  moment at most.

## Adding a language

1. Copy `locales/en.json` to `locales/<code>.json`, where `<code>` is a
   lower-case BCP 47 tag: `es`, `pt-br`, `zh-hant`. A visitor asking for
   `pt-BR` gets `pt-br` when it exists, else `pt`.
2. Fill in `_meta`: `code` (the same as the file name), `name` (in English, for
   the admin console), `nativeName` (in the language itself, for the language
   picker), `dir` (`"rtl"` for Arabic, Hebrew, Persian, ... - the pages then
   render `<html dir="rtl">`), and `machineAssisted: true` unless a native
   speaker wrote or reviewed it (add them to `reviewedBy`).
3. Translate every value in `messages`. Keep each `{placeholder}` exactly as it
   is - the code fills it in (an app name, a number, an email address). Keys
   ending in `.one` and `.other` are the singular and plural forms; `.one` is
   used where the language's plural rules say "one" (`Intl.PluralRules`), so
   for French it also covers 0. Messages are plain text: no HTML, no entities.
4. Import the file in `locales/index.ts` and add it to `LOCALES` - the order
   there is the language picker's.
5. Run `npm test`. `test/i18n.test.ts` fails if the file is missing a key, has
   a key `en.json` does not, changes a placeholder, or leaves a message empty;
   the failure lists the keys.

A key missing at run time falls back to English, so a half-done translation
never shows a key name - but the test keeps that from shipping.

### Adding or changing a string

`locales/en.json` is the source of truth. Add the key there, use it with
`t(locale, "the.key", { vars })` (plain text - escape it) or
`tHtml(locale, "the.key", { vars })` (for a message with trusted markup around
a value), and add the key to every other locale file in the same change: the
test will not pass otherwise. If you cannot translate it, copy the English and
say so in the pull request, so a speaker can follow up. Changing the meaning of
an English message means its translations are wrong too: update or flag them.

The inline scripts (passkey sign-in, Turnstile, the cursor trail) are allowed
by the Content-Security-Policy by hash, so they are never built per language:
text they show comes from `data-` attributes (`data-failed` on the passkey
button, `data-language` on the Turnstile widget). The test checks the scripts
are byte-identical in every language.

## Accessibility

What the pages above do, and the tests that hold them to it
(`test/i18n.test.ts`):

- **Language**: `<html lang>` and `dir` from the negotiated locale; the
  language picker's links carry `lang` and `hreflang`, the current one
  `aria-current`.
- **Structure**: one `<h1>` per page (visually hidden on the sign-in page,
  where the brand's name is the visible heading), the card is the `<main>`
  landmark, the "Protected by" line and language picker a `<footer>`, and
  page titles say what the page is ("Check your email", "Security questions",
  not only "Two-factor authentication").
- **Forms**: every input has a `<label for>`; errors are a live region
  (`role="alert"`) and the inputs they are about get `aria-invalid="true"` and
  `aria-describedby` pointing at them; password fields are described by the
  password policy text; `autocomplete` is `username`, `current-password`,
  `new-password` or `one-time-code` as appropriate; the email code field uses
  `inputmode="numeric"`. (The authenticator field accepts backup codes, which
  contain letters, so it keeps the normal keyboard.)
- **Controls**: the passkey button is a `<button>`, and its status line is a
  polite live region; "Sign in again" and similar are links styled as buttons
  (they navigate), never a button inside a link; the Turnstile widget is a
  labelled group and is asked for the page's language.
- **Focus and colour**: a visible 2px focus outline on links, buttons and
  inputs; the accent is darkened on these pages to `#c2410c` (5.2:1 on white)
  so links and the white text on primary buttons meet 4.5:1; placeholders use
  the muted text colour (4.8:1). All text sits on the white card - a brand's
  gradient is only ever behind it. A brand's custom CSS can undo any of this;
  check contrast when writing one.
- **Motion**: the cursor trail is `aria-hidden`, and off (not drawn, not even
  started) when the system asks for reduced motion.
